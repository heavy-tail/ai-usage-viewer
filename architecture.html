01 — The idea

What it is

If you pay for several AI coding tools at once, each one tracks your remaining quota in a different place, in a different format, behind a different command. There's no single "how much do I have left everywhere?" view. This app is that view.

The defining design constraint is that provider capabilities differ: Codex exposes structured rate limits through app-server, while other tools still expose quota through interactive UI. The app uses a structured local interface when available and otherwise launches an isolated terminal session, drives the usage screen, and validates every extracted section.

02 — The hard part

How it actually reads a CLI

Because these are interactive terminal apps, you can't just capture their output — you have to have a conversation with them. The PTY engine (src/collectors/pty.ts) spawns the program in a pseudo-terminal and runs a scripted sequence of "wait for this text, then type that" steps, plus background "responders" that auto-dismiss prompts like update notices or trust dialogs.

Why "drift" is a first-class concept. Provider output can evolve. When a vendor changes its UI or structured schema, completeness checks fail closed — so the adapter throws a ParserDriftError and the provider is marked drift instead of publishing partial data. The app quietly keeps showing the last verified numbers while a redacted compatibility report records the change for the local monitor, an optional credential-isolated scheduled canary, or a separate repair worker. Autonomous code repair is not bundled in this repository.

04 — End to end

What one refresh looks like

  1. You click Refresh → POST /api/refresh hits the local server.
  2. refreshService takes process and OS-owned named-pipe locks (a second refresh gets 409) and reads the previous snapshot.
  3. Enabled providers collect concurrently, using Codex app-server where possible and isolated PTY conversations elsewhere.
  4. Captured provider output is normalized; terminal output also has ANSI/control codes removed.
  5. A provider-specific parser regex-extracts the percentages → limitFromUsed / limitFromRemaining build a normalized UsageLimit, with a status derived from the numbers.
  6. Results are merged with the previous snapshot: failed providers keep their last numbers but get flagged stale; healthy ones replace.
  7. The whole snapshot is run through redaction (emails, org/account/session IDs) and written to data/usage-snapshot.json.
  8. The redacted snapshot returns to the browser; cards re-render with freshly animated bars.

Status vocabulary

Two independent signals keep the UI honest — the bar shows magnitude, the badge shows alert state.

Limit status
available warning exhausted unknown / unavailable error drift
Bar heat (magnitude)
0–74% used 75–89% used 90–100% used

Bars stay graded even when data is stale, so a glance still tells you who's nearly out.

07 — Why it's built this way

Design decisions that matter

🧪 Dependency injection over mocking

Collectors receive their PTY runner and command runner through a CollectorContext. Tests swap in fakes — no real terminals needed — which is why the tricky logic is actually tested.

📐 Normalize early, render dumb

All provider quirks are resolved in the parser layer into one UsageLimit shape. The React components stay simple and have no provider-specific branches.

🛡️ Redact at the boundary

Nothing reaches disk un-scrubbed. The whole snapshot and every raw dump pass through redactSensitiveText before being written — emails, org/account/session IDs become <redacted-…>.

🔒 Local-only by design

Both the API and Vite dev server bind to 127.0.0.1, and data/ is git-ignored. Your usage never leaves the machine.

♻️ Degrade, don't disappear

A failed refresh keeps the last good numbers, marks them stale, and still grades the bar by saved percentage — the dashboard is useful even when a CLI is down.

🚦 One refresh at a time

An in-flight lock serializes refreshes; the UI queues per-provider requests and polls until the run clears, so concurrent clicks can't stampede the CLIs.

✅ Verify before delivery

Pull requests run parser fixtures, contracts, type checks, an audit, and a production build. A dedicated Windows canary can detect vendor-only drift; tagged bundles are smoke-tested, checksummed, attested, and never silently replaced.
